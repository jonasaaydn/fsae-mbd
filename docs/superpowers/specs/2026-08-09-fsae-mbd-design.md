## 1. 背景と目的

現サイト「MBD×AI Lab」は AI ツールの最新動向を毎日自動生成する媒体だった。しかし運営者（現役のレース車両MBDエンジニア）が
「学生から見ると、入手できないツールばかりで、示される成果も期待できない」と判断した。実データで検証したところ、指摘は正しく、
しかも原因は想定より深かった。

| 検証項目 | 実測 |
|---|---|
| 「実行すると以下が出力されます」と書かれた記事 | 80本（実行の裏付けなし） |
| 模範記事の掲載値と実際の実行結果 | 迎角 9.3° と掲載 → **実測 0.1°**（全数値が不一致） |
| `importance` の分布 | 346/350 が `high`（判別情報として死亡） |
| MBDの中核「状態推定」への言及 | **0本** |
| MBDの中核「車両運動」への言及 | 3本 |
| ツール30件のうち学生が入手できないもの | 約20件。逆に OpenFOAM は74本の記事で使うのに棚に無い |

つまり **MBD の語彙は大量にあるが、車両運動方程式と状態推定という背骨が無い**。AI応用の事例集であって、MBD開発の体系ではなかった。

本設計は、テーマを「**学生フォーミュラ車両のMBD開発**」に定め、既存364記事を全削除してゼロから体系を作り直す。
対象は学生だが内容は易しくしない。実務のレース車両開発と同じ水準（モデルの限界と適用範囲まで）を扱う。

## 3. コンテンツモデル

### 3-1. 章のメタデータ

`src/content/chapters/` に MDX（`.mdx`）を置く。スキーマは `src/content/config.ts` に定義する。
MDX にする理由は 3-4 節（図）を参照。

```yaml
---
part: 1                          # 第I部（V字モデルの工程に対応）
chapter: 2                       # 章番号 ＝ 読む順序
title: "タイヤ：スリップの定義と Magic Formula"
summary: "..."
status: "published"              # planned | draft | published
prereq: ["01-coordinates"]       # 前提章の slug（依存グラフになる）
software: ["MATLAB R2024b", "Simulink"]
toolbox: ["Vehicle Dynamics Blockset"]   # 必要Toolbox。入手性に直結するため必須
math: ["微積分", "線形代数"]
verified_on: "2026-08-09"        # 実際に実行した日。実行した時だけ書く
verified_env: "MATLAB R2024b / Windows 11 / 実行 3.2秒"
---
```

**設計判断: 自己申告の評価値は持たせない。** 現サイトの `importance`（346/350がhigh）と `mbd_relevance`（lowが0本）は、
どちらも「良い側」にインフレして判別情報として死んだ。新スキーマは事実（何が必要か・いつ実行したか）だけを持つ。

**設計判断: 実行記録の別レジストリは作らない。** 現サイトでは `verified-runs.json` を用意したが、
毎日の自動生成を止めたことで書き手が「運営者＋Claude」に限定され、かつ `verified_on` は日付を書くだけで
「高く見せたい」バイアスが働かない。二重管理を避け frontmatter 1か所に集約する。

**`status` が骨格先行を成立させる。** `planned` の章も目次に並び「これから書く」と明示される。
1章目の公開時点で全体像が見える。

### 3-2. 本文の固定テンプレート（全章共通・8ブロック）

| # | ブロック | 内容 |
|---|---|---|
| 1 | この章でできるようになること | 到達目標を1〜3行 |
| 2 | なぜ必要か | レース車両開発のどこで効くか |
| 3 | 理論 | 記号定義 → 式 → 導出。省略しない |
| 4 | 実装 | MATLAB/Simulink、日本語コメント付き |
| 5 | 実行結果 | **自分で実行した出力のみ**。環境を明記 |
| 6 | **限界と適用範囲** | どこまで信じてよいか、いつ破綻するか |
| 7 | 学生チームでの現実解 | 装備が無い場合の代替と、その精度の代償 |
| 8 | 次の章へ | 依存関係の明示 |

**ブロック6が「実務水準」の正体。** 学生向け教材は式の提示で終わりがちだが、実務では
「そのモデルをいつ信じてはいけないか」が本体になる。タイヤ係数を同定できても実測範囲外に外挿した瞬間に嘘になる。
ここまで書くのが本サイトの水準であり、他の教材との差別化点でもある。

**ブロック5の規律**: 実行していない出力は載せない。未実行なら「出力の形式（未実測）」と明示する。
現サイトで80本が犯した失敗を、テンプレートの段階で構造的に防ぐ。

### 3-4. 図（ダイアグラム）

車両運動は図が無いと成立しない。スリップ角もロールセンタも、文章と式だけでは伝わらない。
図の種類ごとに作り方を分ける。

| 図の種類 | 手段 | 理由 |
|---|---|---|
| 座標系・幾何・力の向き（模式図） | **SVG コンポーネント** | 拡大しても劣化せず軽い。文字が検索対象になる。線と色の意味を厳密に統制できる |
| データのプロット（F_y–α 曲線、シミュレーション波形） | **MATLAB で生成 → SVG/PNG 書き出し** | 実測値と一致していなければ意味がない。検証済みデータそのもの |
| ブロック線図・工程図（V字、SIL/HIL構成） | **Mermaid** | 構造図に適し、テキストで管理・修正できる |
| Simulink モデルの画面 | **スクリーンショット** | 実物を見せるのが最良 |

**章は `.mdx` とする**（`@astrojs/mdx` を追加）。理由は、車両運動では同じ図が章をまたいで繰り返し登場するため。
車両上面図は第1章（座標系）・第8章（2輪モデル）・第9章（定常円旋回）・第21章（トルクベクタリング）に現れ、
そのたびに注記だけが変わる。図を引数付きの部品にすれば描き直しが不要になり、
**記号の表記が全章で自動的に揃う**（`/notation/` を独立ページにする設計と整合する）。

```mdx
<TireSlipDiagram alpha={6} showForce />
```

図コンポーネントは `src/components/figures/` に置き、記号・色・矢印の意味を全図で統一する。

| 要素 | 統一規則 |
|---|---|
| 速度ベクトル | 青 |
| 力ベクトル | 赤 |
| 幾何・基準線 | 黒（破線は基準・補助線） |
| 角度 | 円弧＋斜体のギリシャ文字 |

**図の品質担保**: 図は自動生成できるが、そのままでは使えない。試作した1枚でも、ラベルの枠外はみ出し・
矢印と文字の重なり・円弧位置のずれが発生した。**1枚ごとに描画結果を目視で確認する**こと。
あわせて物理の正しさ（力の向きが符号規約と整合しているか）を毎回確認する。
図は誤りが最も気づかれにくく、かつ最も誤解を生む要素である。

## 4. サイト構成

すべて静的生成する。現サイトの `blog/index.astro` は `searchParams` でフィルタしており、
静的出力では常に空振りする死にコードだった。同じ方式は使わない。

| URL | 役割 |
|---|---|
| `/` | 全体像。V字の4部と進捗（例: 全28章中12章公開）、最初に読む章への導線 |
| `/curriculum/` | 目次が主役。部ごとに全章を並べ、未執筆章も `status` 付きで表示 |
| `/ch/[slug]/` | 章本体（例 `/ch/02-tire-slip-definition/`） |
| `/notation/` | 記号表 |
| `/software/` | 必要なソフトと入手方法（MathWorks FSAE 無償申請ルート、Toolbox対応表） |
| `/about/` | 運営者・編集方針・免責 |

**`/notation/` を独立させる理由**: MBD では記号規約が結論を左右する。ISO と SAE で符号が逆になるため、
実測データを読む前に規約を確認しないと結果が反転する。全章が参照する共通言語として独立ページにする。

**章ページのナビゲーション**は `prereq` から自動生成する。

- 冒頭: 「この章を読む前に →（前提章へのリンク）」
- 末尾: 「次に読む →（この章を `prereq` に持つ章の逆引き）」
- 前提章が未公開なら「前提章は準備中です」と表示し、リンク切れにしない

章の冒頭には**「この章に必要なもの」ブロック**を置き、frontmatter の
`software` / `toolbox` / `math` / `prereq` をそのまま表示する。読者が読み始める前に
「MATLAB のどの Toolbox が要るか」「どの数学が前提か」を判断できるようにするための項目であり、
とくに `toolbox` は入手可否に直結する（Vehicle Dynamics Blockset を持たない学生が詰まる箇所を事前に示す）。

**トップページ**は進捗つきの学習地図とする。未完成であることを隠さず「第I部は 3/11 章公開」と出す。
教科書として誠実であり、再訪の理由にもなる。

## 5. 検証と品質担保

- 実行結果は運営者の自宅PC（MATLAB/Simulink 学生ライセンス、SolidWorks、OSS）で実際に実行した出力のみを載せる
- 実行したら `verified_on` / `verified_env` を書く。実行していない章には書かない
- 未実行の出力例を載せる場合は見出しを「出力の形式（未実測）」とし、「実行すると以下が出力されます」とは書かない
- 数値には出所を付ける。許容するのは (1) 自分で実行した値 (2) 一次ソースURL付きの仕様値・出典値 (3) 空欄「あなたの環境: ___」の3つだけ

## 8. 検証方法（この設計が正しく実装できたかの確認）

1. `npm run build` が成功し、`dist/` に `/curriculum/`・`/ch/*/`・`/notation/`・`/software/` が生成される
2. `status: planned` の章が目次に表示され、章ページは「準備中」として成立する（404にならない）
3. `prereq` を持つ章で、冒頭に前提章リンク・末尾に後続章リンクが自動表示される
4. 前提章が未公開の場合、リンク切れではなく「準備中」と表示される
5. 旧URL `github.io/mbd-ai-lab/` からのアクセスが新URLにリダイレクトされる
6. `verified_on` を持つ章にのみ実行環境が表示される
7. 記事本文に「実行すると以下が出力されます」という表現が1件も存在しない
8. `.mdx` の章に図コンポーネントを埋め込んで描画され、拡大しても劣化しない
9. 図のラベルが枠外にはみ出さず、矢印と文字が重ならない（1枚ずつ描画結果を目視で確認）
10. 図の色分けが規則どおり（速度＝青／力＝赤／幾何＝黒）で、全図を通して一貫している
