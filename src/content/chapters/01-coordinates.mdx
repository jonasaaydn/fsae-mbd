## この章でできるようになること

- 車両座標系（原点を重心に置き、x・y・zの3軸で車両の運動を表す枠組み）を、図と数式の両方で定義できる。
- ISO 8855とSAE J670（従来のJ670e）の符号規約の違いを、軸の向きと具体的な物理量（横加速度・ヨーレート）の符号の両方で説明できる。
- 一方の規約で取得したデータを、変換行列を使ってもう一方の規約に変換できる。

## なぜ必要か

車両運動を扱うすべての章は、この座標系の上に成り立っています。ところが実務では、データロガー・CAEツール・文献のそれぞれが、必ずしも同じ符号規約を使っているとは限りません。ISO 8855とSAE J670（従来のJ670e）は、どちらも「x軸は前方」で一致していますが、y軸とz軸の向きが逆です。この違いに気づかないまま横加速度やヨーレートの符号を読むと、次のような実害が起こります。

- 旋回方向（右旋回か左旋回か）を、グラフの符号だけから判断すると、逆に読んでしまう。
- 横加速度とヨーレートの符号の関係から車両の挙動（アンダーステア寄りかオーバーステア寄りか）を診断するとき、判定が反転する。
- 走行データのロガーとSimulinkの車両モデルなど、複数のツールの出力を重ねてグラフ化したときに、符号が逆のまま比較してしまい、実際には一致しているモデルとデータを「合っていない」と誤診断する。

これらはいずれも計算そのものが間違っているのではなく、同じ物理量を指す2通りの表現を混同していることが原因です。だからこそ、車両運動の章を1つでも読み進める前に、座標系そのものを最初に固定しておく必要があります。

## 理論

### 車両座標系の定義

車両座標系は、原点を車両の重心（CG）に置き、x軸を車両前後方向、y軸を車両横方向、z軸を車両上下方向に取る右手系の直交座標系です。前後方向（x）の向きは、ISO・SAEのどちらの規約でも「前方が正」で一致しています。違いが出るのはy軸とz軸です。

### ISO 8855

**ISO 8855**（Road vehicles — Vehicle dynamics and road-holding ability — Vocabulary）は、x前方・y左・z上向き（Z-up）の右手系を規定しています（[ISO 8855:2011](https://www.iso.org/standard/51180.html)）。本サイトはこの規約を基本とします。

### SAE J670（従来のJ670e）

**SAE J670e**（従来版）は航空分野の慣習を引き継ぎ、x前方・y右・z下向き（Z-down）の右手系を使います。2008年改訂のSAE J670は、ISO 8855との整合を図り、Z-up・Z-down双方の向きを許容する形に改められました。したがって「SAEに準拠している」という記述だけでは、実際にどちらの軸の向きが使われているかを一意に確定できません。データを受け取ったら、どちらの向きかを個別に確認してください。

図1-1・1-2のとおり、両者はx軸を共有したまま、yとzの符号が反転します。この関係は、変換行列

`T = diag(1, −1, −1)`

で表せます。展開すると次の形になります。

```text
    ⎡ 1   0   0 ⎤
T = ⎢ 0  −1   0 ⎥
    ⎣ 0   0  −1 ⎦
```

`diag(1, −1, −1)`の行列式は+1（固有回転）であり、鏡映（行列式−1の変換）ではなく、x軸まわりの180°回転に相当します。そのため、位置・速度・加速度のような通常のベクトルだけでなく、ヨーレート`r`のような角速度（擬ベクトル）も、同じ`T`を掛けるだけでISO⇔SAE間を変換できます。鏡映変換であれば擬ベクトルにだけ余分な符号反転が必要になるところですが、今回はその心配がありません。また`T² = I`（`T`はそれ自身の逆行列）なので、ISO→SAEとSAE→ISOは同じ行列で行き来できます。

本サイト全体で使う記号の一覧は[記号表](../../notation/)にまとめています。`y`・`z`・`a_y`・`r`の定義はこの章の内容と一致させています。

## 実装

以下のMATLABコードは、上で導いた変換行列`T`を使って、同じ物理現象（左旋回中の横加速度とヨーレート）をISO表記とSAE表記の両方で表し、`T`が自分自身の逆行列であること（`T² = I`）を確認します。base MATLABの機能（`diag`・`fprintf`・`disp`・`isequal`・`eye`と行列積）のみを使用しており、追加のToolboxは不要です。

```matlab
% ISO 8855 と SAE J670 の相互変換
% ISO 8855: x 前方 / y 左 / z 上向き（Z-up）
% SAE J670e（従来）: x 前方 / y 右 / z 下向き（Z-down）
% → y と z の符号が反転する（x は共通）

T = diag([1, -1, -1]);   % ISO <-> SAE の変換行列（自分自身が逆行列）

% 例: 左旋回中の横加速度とヨーレート（ISO表記）
a_y_iso = 8.5;    % m/s^2  左向きが正（ISO 8855）
r_iso   = 0.62;   % rad/s  上から見て反時計回りが正（z 上向きのため）

v_iso = [0; a_y_iso; 0];
v_sae = T * v_iso;

fprintf('--- 同じ左旋回を2つの規約で表す ---\n');
fprintf('ISO: a_y = %+.2f m/s^2,  r = %+.3f rad/s\n', a_y_iso, r_iso);
fprintf('SAE: a_y = %+.2f m/s^2,  r = %+.3f rad/s\n', v_sae(2), -r_iso);
fprintf('\n変換行列 T:\n');
disp(T);
fprintf('T*T = I か: %d\n', isequal(T*T, eye(3)));
```

`a_y`と`r`の符号をどちらも`diag([1, -1, -1])`で一括変換できるのは、この行列が理論セクションで示した固有回転（鏡映ではない）だからです。コード中では`v_iso`をベクトルとして`T`で変換する一方、`r_iso`はスカラーとして直接`-1`倍していますが、これは`r`がベクトル`v`のz成分と同じ変換則（−1倍）に従うことを踏まえた書き方です。

## 限界と適用範囲

本章で扱ったのは車両座標系（vehicle-fixed coordinate system）の符号規約に限られます。実務でデータを扱うときは、次の2点にさらに注意してください。

**1. タイヤ座標系は、車両座標系と独立に規約が選ばれうる。** [ISO 8855:2011](https://www.iso.org/standard/51180.html)の改訂は、車両座標系だけでなく、タイヤ・ホイールに固定した座標系（tyre axis system）の規定も別途拡張しています。タイヤ座標系のスリップ角・スリップ率・タイヤ力（`F_x`・`F_y`・`F_z`）の符号は、車両座標系の符号規約とは別に決まります。そのためデータ提供元（タイヤメーカーの試験機、CAEツールのタイヤモデル）が、車両側はISO・タイヤ側は別の慣習、という組み合わせでデータを出してくる可能性があります。車両座標系がISOだからといって、タイヤ座標系も自動的にISOだと決めつけないでください。第7章（タイヤスリップ）以降でタイヤ座標系を扱う際に、改めてこの点を確認します。

**2. 符号規約は、データの数値そのものからは判定できない。** `a_y`や`r`の時系列データだけを見て「これはISOかSAEか」を機械的に判定する方法はありません。判定に使えるのは、既知の挙動（どちら向きに旋回したかが分かっている試験）と符号を突き合わせることだけです。ロガーのマニュアルやCAEツールの設定に「ISO準拠」と書かれていても、設定ミスや初期設定の変更で実際の出力が食い違っている可能性は残ります。次のセクションで、この確認を具体的にどう行うかを示します。

## 学生チームでの現実解

データロガーを持つ学生チームが、自分たちのデータがISOかSAEかを実際に確定させる手順は次の通りです。

1. **まずロガー・CAEツールの設定画面とマニュアルを確認する。** 多くのロガーは、チャンネルごとに符号規約を設定・表示できます。ここで規約が明記されていれば、それを起点にできます。ただし設定は変更されうるので、次のステップの実測確認を省略しないでください。
2. **既知の方向の定常円旋回を1本走る。** コーンなどで明確に旋回方向が分かるコース（例：右回りのスキッドパッド）を設定し、一定舵角・一定速度で数周します。
3. **その区間の`a_y`と`r`の符号を確認する。** 本章の理論に従えば、右旋回であればISO表記の`a_y`と`r`はどちらも負、SAE表記であればどちらも正になります（左旋回であればこの逆）。実測データの符号がどちらのパターンと一致するかを見れば、そのロガーが実際にどちらの規約で出力しているかが分かります。
4. **判明した規約を、チームのデータ処理コードとWikiに明記する。** 変換が必要な場合は、本章の`T`と同じ形の変換行列を前処理スクリプトの先頭に置き、以後すべての解析がこの前処理を経由するようにします。個々のグラフを描くたびに符号を手で直す運用は、いずれ必ず取り違えます。
5. **複数のツールを併用する場合は、ツールごとに同じ確認を独立に行う。** ロガーとCAEツール（Simulinkの車両モデルなど）を重ねて比較する前に、両方の規約を個別に確認してください。「両方ともISOのはず」という思い込みが、本章冒頭で挙げた実害の典型的な原因です。
